## 官方示例与实际实现

官方 [cartesian_impedance_control.cpp](https://github.com/RokaeRobot/xCoreSDK-CPP/blob/main/example/rt/cartesian_impedance_control.cpp) 使用 `setCartesianImpedance`、`setCartesianImpedanceDesiredTorque`、`setFcCoor`，再以 `cartesianImpedance` 模式发送平衡位姿。它包含自动上电、移到示例关节姿态、非零期望力和大幅轨迹，不应原样用于本装配。当前官方 main 示例与本地 SDK 0.3.4 不是同一版本；上述接口已与本地 [头文件](../sdk/include/rokae/motion_control_rt.h) 交叉核对。

本项目已经实现真实 SDK 路线，不需要另写一个位置伺服来模拟弹簧：

```text
Quest 相对位姿 → 遥操作门控/参考映射
 → ImpedanceController：相对实测 TCP 限制平衡点距离
 → Python 驱动发布最新平衡位姿
 → C++ 1 kHz 回调：再次按实测 TCP 限制距离
 → xCore cartesianImpedance → 控制器执行柔顺运动
```

实现见 [Python 控制器](../control/controllers/impedance.py) 与 [C++ 驱动](../src/rokae_driver.cpp)。本路线绕过主机 Pinocchio 微分 IK；七轴阻抗命令没有锁定 `hasElbow`，不能假定肘部始终保持原姿态。启动后不支持位置/阻抗热切换，应退出后重启。

当前构建支持按主机选择 x86_64/aarch64 SDK；不能将历史 Orin 平台结论套用到当前 x86 主机。当前没有实现自定义力矩控制所需的完整动力学接口。

## 与 Franka 弹簧阻尼的关系

概念上是围绕平衡位姿的弹簧与阻尼，接触时允许位姿偏离。Franka 的 [官方示例](https://github.com/frankarobotics/libfranka/blob/main/examples/cartesian_impedance_control.cpp) 在应用层计算刚度/阻尼力矩；这里交给 ROKAE 原生控制器执行。本地 0.3.4 接口能设置六轴刚度，但没有独立的笛卡尔阻尼或虚拟质量设置接口，不能声称支持与 Franka 相同的任意 K/D/M 调节。

| 配置 | 当前值 | 意义 |
| --- | --- | --- |
| `stiffness` | `[300,300,300,15,15,15]` | 前三项 N/m，后三项 Nm/rad；试验占位值，未做真机接触验收 |
| `desired_wrench` | 六项零 | 不叠加主动期望接触力；不代表实际接触力为零 |
| `reference_limit.translation` | 0.04 m | 平衡点相对实测位置的最大距离 |
| `reference_limit.rotation` | 0.30 rad | 平衡点相对实测姿态的最大角距离 |
| `mock_mass` / `mock_damping` | 仅仿真 | 不会设置真机负载或阻尼 |

SDK 刚度上限为 `[1500,1500,1500,100,100,100]`，期望力/力矩范围为前三项 ±60 N、后三项 ±30 Nm。上限不是推荐试验值。当前力控坐标系为单位变换的 world；并非照片中传感器标出的 Y+ 坐标系。

以平移刚度 300 N/m 为例，10 mm 偏差的静态弹簧项约 3 N；40 mm 对应约 12 N。**这不是总接触力安全上限**，未计入惯性、阻尼、负载误差、旋转力矩和接触杠杆。参考限幅在受阻时会限制持续累积误差，表现也不同于无限偏差的固定弹簧。

SDK `setCollisionBehaviour` 注释说明该接口的碰撞检测在位置控制生效、力控不生效；不能扩展为所有安全保护关闭。关节限位、实时通信、控制器故障等仍可能停止或下电。这里没有提高碰撞阈值，也不能保证任意碰撞都不断电。

## 负载、TCP 与 KWR75B

启动原生路线会读取并打印控制器当前 toolset 的质量、重心、惯量。SDK 有 `setLoad` 和 `setEndEffectorFrame`，但当前 Python 桥没有暴露这两个设置入口，启动日志也不能证明参数已正确标定。先称重/辨识整套负载、核实实际 TCP 与控制器参数；不可只改 `mock_mass`。

当前 KWR75B **尚无数据接收、去零、重力补偿或反馈闭环实现**；ROKAE 原生阻抗不依赖读取该外置传感器。若下一步需要定量接触力监测或恒力任务，应先确认具体通信版本，再接入带时间戳的六维力，完成偏置、负载、坐标旋转及力矩平移变换，然后先记录验证，再考虑导纳/力控外环。避免未经验证把外环叠加到原生阻抗上。

灵巧手仍发送位置寄存器命令；机械臂柔顺不会自动使手指具有阻抗控制。

## 启动与验收

在已核实负载/TCP、实时通信和作业空间后，用现有独立控制选项启动，无需复制整份机器人或任务配置：

```bash
conda activate /data/miniconda3/envs/dexteleop
python -m dexretarget \
  --task-config config/tasks/cup.yaml \
  --enable-hand --enable-arm \
  --arm-control impedance --no-capture --skip-init
```

`--skip-init` 跳过启动回 home，不代表不上电或不启动实时控制。初始化后默认暂停跟随，`e` 使能、`p` 暂停、`q` 退出；`h` 仍是任务关节回位，不是阻抗柔顺回位。首次接触验证期间不要用 `h` 推离障碍物。

建议先保持当前平衡位姿，在无接触状态核实无异常漂移，再分方向小幅接触确认恢复方向、振荡及肘部行为；实测稳定后再启用 Quest 跟随，逐步验证抓取。暂停/丢帧保留目标不等于刚性锁死，阻抗下外力仍可能使手臂偏移。

采集时将 `--no-capture` 改为 `--capture`；该路线的臂 action 是平衡位姿，与实测 TCP 的差值有物理意义。字段格式不变，但训练时应按控制模式区分数据，不能把位置控制与阻抗数据不加区分地混合。现有 mock 验证只检查软件链路，不能证明真实接触稳定性。

2026-10-22 21:49:05 41440 阻抗开启，碰撞检测将会被关闭
2026-10-22 21:49:05 41470 力控保护参数已设置为默认值

### 负载会不会让手臂向上漂

会存在这种可能：质量、质心、重力方向或本体模型错误会使补偿力矩与真实重力矩不匹配。若其他条件正确，质量高估可产生向上的偏置；质心错误还会产生姿态和各关节力矩误差。但当前已验证的是数值传输正确，不是标定物理准确；必须独立称重/核实质心参考系与本体安装参数，不能靠“漂了就减重量”调参。

一个仅用于量级理解的单轴静态模型：质量误差 0.1 kg 在 K=300 N/m 时对应约 3.3 mm 平衡偏移（Δz≈Δm·g/K）。实际七轴机器人还受关节动力学、姿态和零空间影响，这个估算不能预测失稳或认定根因。零惯量影响动态模型，但静止重力补偿主要依赖质量与质心；不能断言补任意惯量就能修复。

### 惯量是否必须辨识

必须区分“合理负载动力学参数”和“必须通过自动辨识得到”。惯量可以来自有效辨识、厂家数据或符合接口参考系/单位的 CAD 质量属性；自动辨识不是唯一来源。当前未查到 xMatePro3 / xCore 2.3.2 官方条款要求先完成自动工具惯量辨识才允许 Cartesian impedance。SDK 接受零惯量亦不能证明当前装配使用零惯量是正确的。

物理上静止重力项主要依赖质量与重心，惯量参与加速度相关响应。当前启动抬升不能仅因惯量为零就定因，但惯量仍是未验证参数。Franka 示例“without inertia shaping”表示不主动塑造任务空间惯量，不表示不需要合理的工具/负载模型。参见 [Franka setLoad](https://frankarobotics.github.io/libfranka/latest/classfranka_1_1Robot.html)。

### ER3 Pro / xMatePro3 升级调研

官方 [升级与备份流程](https://docs.rokae.com/docs/xCore/14-%E9%80%89%E9%A1%B9/) 是获取匹配安装包、连接控制器/升级服务、备份、上传、重启。HMI 不匹配会提示推荐版本，机器人配置文件不匹配可能禁止运动。PC 版 RobotAssist 安装更新与控制器固件更新不是同一项；文档中的“HMI升级”菜单针对 xPad2。操作步骤较短不代表从本机 2.3.2 跨版本升级已经确认兼容。

官方 V3.1/V3.2 手册提及负载惯量计算，但没有找到“旧 ER3 Pro 从 2.3.2 升到指定版本后新增完整工具惯量自动辨识”的发布说明或支持矩阵。不能把手册版本号当作功能在本机的保证，也不能因升级 RobotAssist 就保证控制器增加算法。

[SDK 版本记录](https://github.com/RokaeRobot/xCoreSDK-CPP/blob/main/CHANGELOG.md) 声明：0.6.0 要求 xCore>=3.1.0，0.7.0 要求 >=3.2.0；更新 SDK 不等于更新机器人固件。本项目运行的是 0.3.4，不能未经兼容性确认直接用新 SDK 替换。当前没有执行下载升级包、刷写或重启。

应向厂家一次确认：

1. 本机 ER3 Pro/xMatePro3 + 控制柜/IPC 硬件 + xCore 2.3.2 可升级的推荐版本、是否需中间版本、匹配 RobotAssist（优先 Ubuntu 包）和 SDK。
2. 推荐版本是否对这个旧机型自动辨识 Ixx/Iyy/Izz，是否输出惯性主轴方向；哪些量只支持手工/CAD 输入，适用单位与参考点是什么。
3. 当前两步辨识保存后 I=0 是否为此机型预期行为；原生固定参考阻抗约 0.11 秒内抬升且 J2 到 0.151 rad/s，应检查哪些本体动力学/传感器项及已知固件问题。
4. 升级前应备份/保留的本体参数、机械零点、力矩传感器标定、工程和工具，以及回退路径。

结论：目前不以“必须惯量辨识”为理由升级；先根据该固定参考试验定位启动补偿/控制器模型问题，不增大护栏来让异常运动持续更久。
