三层状态必须区分：

| 层次 | 读取/设置 | 本项目行为 |
| --- | --- | --- |
| RobotAssist RL 工程工具 | `FcInit tool1,wobj0,0` 引用工程工具 | 保存工具不代表 SDK 自动选中它 |
| SDK 活动工具 | `robot.toolset()` / `robot.setToolset()` | true 时覆盖质量/重心；保留 TCP、工件坐标、惯量；false 时只核验 |
| 实时负载 | `rt->setLoad(active.load)` | 进入 RT 后显式传入整份活动负载；API 成功不等于内部动力学独立回读 |

本地 `rokae/sdk/include/rokae/robot.h` 说明 SDK Toolset 不与 RL 工程相关；RobotAssist 右上角更改默认工具工件会更新 SDK 活动值。按名称选择工具要求已加载含该工具的 RL 工程。`motion_control_rt.h` 说明 RT setLoad 的设置由控制器保存，机器人重启后恢复默认，并没有承诺每次启动阻抗自动读取 RL 工具。

[官方 RT 故障排查](https://docs.rokae.com/docs/SDK/cpp/实时模式常见问题/cpp_rt_error_and_exception_handling/) 明确要求开启实时模式后使用 RT setLoad，并区分算法模型、力控模块的同名接口。在线页面为 0.7.x，作为官方用法参考；不能据此排除旧控制器缺陷，也不能直接换用新版库。

离线检查本地 x86_64 `libxCoreSDK.nomodel.so.0.3.4`：`RtMotionControlCobot<7>::setLoad` 的反汇编范围 `0x10de40..0x10e06c` 将输入质量、重心、惯量组成请求，经 XService 写入 `load`；没有读取旧工具质量再相加的计算。`BaseRobot::setToolset` 则序列化工具内的 load 和坐标参数，写入 `ix.coord.toolset`。该证据只覆盖主机 SDK 发送端，两个请求名称不同不能证明控制器内部补偿独立或正确。被检查库 SHA256 为 `270614ea618179b41983f65831732af156bae1533ce27f80b0e92e028af24650`。

## 最新实读与几何约束

2026-10-23 17:16 再次通过 SDK 读取，当前法兰位置 `[536.917161,0.000010,613.852055] mm`，关节姿态已改变，因此本次位置不再与图 1 相同。此前 15:33 保存的读数与图 1 一致。新读取的 TCP 平移/旋转仍全零，工具系与法兰系重合；位姿链闭合平移残差约 0.000137 mm。查询前后均为上电、idle，没有发送模式、负载、上电或运动设置。活动 SDK Toolset 本次仍读为 0 kg，这与截图保存的工具参数是不同状态，不能混为一份数据。

原始重心的轴向距离为 8.610 mm，横向距离 `sqrt(x²+y²)=54.099 mm`；从法兰中心指向重心的向量与 +Z 夹角约 80.96°，几乎沿法兰平面。图 3 则显示主要负载在法兰轴向外侧。

进一步使用[因时官方 RH56DFX-2R 标称质量 540 g](https://en.inspire-robots.com/product/rh56dfx/)做质量加权约束。假设图 3 是相同装配，且其余负载质心也在法兰外侧（Z≥0）：

```text
M * z_total = m_hand * z_hand + Σ(m_other * z_other)
z_hand ≤ M * z_total / m_hand
       = 0.939386 * 8.609842 / 0.540
       ≈ 14.98 mm
```

也就是说，原始结果要求灵巧手自身质心距机器人法兰轴向不超过约 15 mm。照片中手前面已经有力传感器和多层转接件，手自身还沿外侧延伸，该约束与装配明显不符。这比仅凭“哪个轴数值最大”更有力。厂家标称质量不是现场称量；若有大量质量位于法兰背面或线缆施加外力，应单独计入。不过以手质心 Z=100 mm 为一个示例，原始结果要求剩余约 0.399 kg 的平均 Z=-115 mm，与图示主体装配难以相容。

即使把总重心 Z 改为 52.710 mm，同样条件下手自身质心也必须满足 Z≤91.70 mm；若实际手质心更远，候选值仍偏小。因此“原值不合理”并不能推出“仅交换三个分量即可修正”。轴/参考点解释不一致、辨识偏差、线缆力或未使用同一工具都需要考虑。SDK 官方字段和本地传参没有发现 XYZ 重排；不能把这种冲突直接认定为 SDK 的通用轴顺序错误。

原始数据与计算见[本次几何复核](../../docs/validation/run_history.md)。最简单的现场几何检查是测量机器人法兰面到灵巧手安装面的轴向距离：若它已超过 15 mm，且手的质量均位于该安装面外侧、其他主要负载也在 Z≥0，则原始 Z=8.61 mm 与质量分布不相容。该检查无需让机械臂运动。

## 坐标定义与原始数据

质量为 0.93938639463 kg。原始截图 XYZ 为 `[-52.71043598571,12.17669684527,8.60984186271] mm`；配置仅除以 1000 转为米，没有交换轴或修改符号。

ROKAE [SDK 与示教器功能对应](https://docs.rokae.com/docs/SDK/sdk_assist/) 的 SetLoad 将 Rx/Ry/Rz 定义为法兰坐标系中的距离；[官方早期 xCore 手册](https://static.rokae.com/Downloads/Manual/xCore%20Control%20System%20User%20Manual-V1.5.1.pdf) 的工具示例也分别给出 TCP 与相对法兰原点的重心偏移。在线手册存在版本差异；本次仍以本地 SDK 0.3.4 接口、用户确认的辨识时 TCP 全零及已保存的实读为依据，不把新版 API 当作旧版本已验证能力。

工具 TCP、负载重心、力控任务坐标是三个不同参数。一般点坐标变换为 `c_flange = p_flange_tool + R_flange_tool * c_tool`；不能只按照世界坐标箭头重排分量。用户确认辨识时 TCP 平移/旋转全零；[最近的法兰/工具实读](../../docs/validation/run_history.md) 也是单位 TCP 变换，且与 `tcp-axis.png` 数值相符。因此在已知条件下，工具系与法兰系之间没有需要补偿的旋转。

[ER3 Pro 官方硬件手册](https://static.rokae.com/Downloads/Manual/xMate%20ER3%20Pro%E7%A1%AC%E4%BB%B6%E5%AE%89%E8%A3%85%E6%89%8B%E5%86%8C.pdf) 第 3.2.3 节规定：法兰 +Z 垂直法兰向外，+Y 由 Pilot 中线确定，+X 按右手定则。该坐标系随法兰转动，不能以照片上下方向代替；KWR 外壳 Y+ 也不能直接代替机器人法兰 +Y。

## 对候选值的判断

装配照片中大部分组件沿法兰外侧伸出，因此怀疑原始 Z=8.61 mm 值是否符合实际，具有几何依据。但照片不提供法兰上 X/Y 正向的可靠定位、每个组件质量/质心、轴向尺寸与线缆受力，无法确认新数值或符号；即使 Z 应更大，也不能推出 Z 必须等于原 X 的绝对值。

若把候选解释为固定轴重命名，它要求 `x_new=y_old, y_new=z_old, z_new=-x_old`。其矩阵为：

```text
P = [ 0  1  0
      0  0  1
     -1  0  0 ], det(P) = -1
```

这是反射，不是两个右手坐标系之间的旋转。注意：这不能证明候选重心本身不可能，也不能排除另一种真实三维旋转将某一个向量变成候选；它说明这种“换轴再把负数变正”的解释没有成立。若原辨识有误，也应重新测量或核对正常工作工具，而非使用该矩阵修补。

两组候选都距法兰原点 54.78 mm，但代表的物理点相距 78.54 mm。在此前独立试验 home、基座 +Z 向上假设下，重心相对法兰的基座高度分别为 +20.30 mm 和 -51.27 mm；后者从照片直觉看更像向外伸出的装配，但这不是三维测量结论。两组模型在该姿态下的负载重力矩差约 0.298 Nm；所有姿态下差值上界约 0.723 Nm，仅为负载关于法兰的重力矩差，不是各关节的力矩阈值，也不能证明它导致先前保护。

## SDK 与 RobotAssist 的差异及代码修正

官方 [RL 力控指令](https://docs.rokae.com/en/docs/xCore/rl-%E6%8C%87%E4%BB%A4/%E5%8A%9B%E6%8E%A7%E6%8C%87%E4%BB%A4/) 的 `FcInit(Tool,Wobj,ForceFrameRef)` 显式引用工具。SDK Toolset 则是 SDK 运动控制使用的状态，保存 RL 工具不代表 SDK 已选中同一份参数。此前实读活动 SDK 质量为 0 kg；配置中正质量与重心在本项目阻抗启动时通过 `setToolset` 写入，再读回，并通过 RT `setLoad` 传给实时模块。应用层没有累加两份质量；API 成功仍不能独立证明控制器内部不存在重复补偿，详见上方最新审查。

本次发现并修正遥操作分支的两处顺序差异：

1. 阻抗启动改为与本地官方示例相同的 `automatic → RtCommand → power on`；位置控制路线保持既有顺序。
2. 改为先 `setFcCoor`，再 `setLoad → setCartesianImpedance → setCartesianImpedanceDesiredTorque`，最后启动回调。力控坐标初始化位于增益设置之前，减少对初始化状态的隐含依赖。不声称此前顺序必然造成重置或就是漂移根因。

独立固定参考试验本来已经采用上述顺序，现场仍曾漂移触发软件护栏。因此这两处修正不能解释全部失败，也不意味着可以立即重新运行整套遥操作。
